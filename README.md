# LegendCraft — Resource Pack

The **server-required** resource pack: custom item models, textures, and sounds for
every LegendCraft plugin. Authored by us (per `LegendCraft/Design/plugin-strategy.md §4`);
`ModelEngine` will later hand us merge-ready assets for rigged **mob** models.

- **Target:** Paper **26.1.2** — pack format **84** (`resource_major` from the server's
  `version.json`). Bump `src/pack.mcmeta` when the server's resource major changes.
- **Mechanism:** the **modern item-model system** — the `minecraft:item_model` data
  component points an item at an *item model definition* under `assets/legendcraft/items/…`.
  We do **not** use the legacy `CustomModelData` + predicate-override style (most online
  tutorials still show it; it will not match 26.x). See §4 of `PLUGIN_STRATEGY.md`.

## Asset identity is owned by Core's `ModelRegistry`

`LegendCraft-Core`'s `com.legendcraft.core.assets.ModelRegistry` is the single authority
for asset identity (`ENGINEERING_STANDARDS §18`). This pack's folder layout **mirrors it
exactly** — a plugin resolves a key there, and it must resolve to a file here:

| Core call | Model key | File in this pack |
|-----------|-----------|-------------------|
| `ModelRegistry.modelKey(CLASSES, "sniper_arrow")` | `legendcraft:classes/sniper_arrow` | `assets/legendcraft/items/classes/sniper_arrow.json` |
| `ModelRegistry.modelKey(ECONOMY, "marks")` | `legendcraft:economy/marks` | `assets/legendcraft/items/economy/marks.json` |

Domain = the first path segment. Reserved domains (from `ModelRegistry.Domain`):
`core`, `classes`, `factions`, `economy`, `world`. **Never invent a domain here that
Core doesn't reserve**, and never rename one — the pack is shipped and the paths are
load-bearing.

## Layout

```
src/
  pack.mcmeta                         pack format + description
  pack.png                            pack icon (generated by build.ps1 if absent)
  assets/legendcraft/
    items/<domain>/<name>.json        item MODEL DEFINITION (what item_model points at)
    models/item/<domain>/<name>.json  the item MODEL (parent + textures)
    textures/item/<domain>/<name>.png the texture
    sounds/<domain>/…                 custom sounds (+ sounds.json) — later
```

### Adding a flat (sprite) item — the three files

For `legendcraft:<domain>/<name>` a plugin sets on the ItemStack:
`item.setData(DataComponentTypes.ITEM_MODEL, Key.key("legendcraft", "<domain>/<name>"))`.

1. `items/<domain>/<name>.json` — the definition the component resolves to:
   ```json
   { "model": { "type": "minecraft:model", "model": "legendcraft:item/<domain>/<name>" } }
   ```
2. `models/item/<domain>/<name>.json` — a flat generated sprite:
   ```json
   { "parent": "minecraft:item/generated",
     "textures": { "layer0": "legendcraft:item/<domain>/<name>" } }
   ```
3. `textures/item/<domain>/<name>.png` — the 16×16 (or 32×/64×) texture.

`CustomModelData` (the integer ranges Core also reserves) is only for **variant dispatch
on a shared vanilla base item** via a `range_dispatch`/`select` model — not needed for a
fully-custom item, which uses `item_model` as above.

## Build & deliver

```
pwsh -File build.ps1          # zips src/ → dist/LegendCraft-Pack-<version>.zip + .sha1
```

`build.ps1` prints the SHA1. Delivery is plugin-side (preferred: the Paper API
`ResourcePackPushEvent` / `player.setResourcePack(url, sha1, required)` — versioning,
kick-on-decline, per-world packs), which will live in a Core/delivery module. For a quick
local test, host the zip and set `resource-pack` / `resource-pack-sha1` in
`mc-dev/server/server.properties`.

`VERSION` holds the pack's semver; bump it when assets change so clients re-download.

## Rig staging (`deploy-rigs.ps1`)

```
pwsh -File deploy-rigs.ps1 -Rig <name>[,<name>...]     # → dist/rigs/models/ + VERIFY.md + STAGE-READY
pwsh -File deploy-rigs.ps1 -Preflight                  # exit 0 = that stage is safe to copy
```

Stages `.bbmodel` rigs out of `mobs-src/` into the flat folder BetterModel wants, and writes
the runbook you work through at the box. **It never deploys** — the copy into
`plugins/BetterModel/models` is your step, under the deploy lock, and `dist/rigs/VERIFY.md`
is the sequence (lock → preflight → copy → restart → pack merge → restart → `baseline` →
per-rig checks → `verify` → `release`). Run the preflight before copying: presence of
`STAGE-READY` alone does not mean the folder is intact.

Rig names are arguments rather than a built-in list — this repo is published and `mobs-src/`
deliberately is not. Full contract and the test command are in `TOOLING.md` (tracked).

The eight Scarlands rigs:

```
pwsh -File deploy-rigs.ps1 -Rig wept,glassjackal,sorrowmoth,eyeless_warden,grief_of_stone,choir_of_salt,iron_reaver,reaver_lieutenant
```

## Dev pack publishing

`tools/merge_dev_pack.py` (durable, re-runnable) builds `dist/LegendCraft-Pack-dev.zip` —
the pack mc-dev points at — by merging BetterModel + BetterHud generated packs with our
built pack, preserving every source's `pack.mcmeta` OVERLAYS (dropping BetterHud's is
exactly how the HUD broke on 2026-08-03). Run `build.ps1` first, run this after the server
has booted with the current models, upload with `gh release upload dev ... --clobber`, pin
the printed sha1 in mc-dev `server.properties`, restart.
